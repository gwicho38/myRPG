## 1. Chapter / Vertical-Slice Structure (pacing the first hour, act shape)

**Confidence: High** (multiple converging craft sources; well-established narrative theory).

1. **Use a compressed three-act shape for one chapter: inciting incident → rising beats → climax → short resolution.** Three-act structure subdivides each act into "beats" (a nine-beat skeleton). The **inciting incident** ("call to adventure") is the catalyst that forces the protagonist's first choice and starts the journey; **Act 2 holds the bulk of gameplay** (challenge ratchets up, tests learned skills); Act 1 should be ~25% of the runtime but you have only ~10 minutes to grab the player. For Neverquest's existing 3-act `StoryFlag` enum, this maps directly: Act 1 = onboarding + first quest at the hub, Act 2 = biome excursions, Act 3 = climax/boss + resolution back at the hub. *Sources: [gamedesignskills.com three-act](https://gamedesignskills.com/game-design/three-act-structure/), [balagan.info 3-act for RPG scenarios](https://balagan.info/3-act-story-structure-for-rpg-scenario-design)*

2. **Structure the chapter as a sequence of discrete "beats," each a single area/event/activity.** "A beat is a small self-contained chunk of a level. A single area, event, activity, or element." Beats combine into rhythm like music. This is the practical unit of a chapter plan — one beat ≈ one Neverquest scene/quest step. *Source: [The Level Design Book — Pacing](https://book.leveldesignbook.com/process/preproduction/pacing)*

3. **Open low-intensity; reserve the first 10–15 minutes for acclimation.** "Begin your game or level with something low intensity, like an introductory cutscene or some low stakes exploration." Use it for control familiarization + worldbuilding before escalating. Neverquest already has `IntroScene` → `MainMenuScene` → `MainScene`; the *first playable beat* should be safe, low-stakes (e.g., the hub/Crossroads with one NPC and one objective), not a combat biome. *Source: [Level Design Book — Pacing](https://book.leveldesignbook.com/process/preproduction/pacing)*

4. **Build an intensity graph and alternate high/low; never sustain max intensity 10+ min.** Plot time (x) vs. intensity 0–10 (y). "Players adjust to prolonged periods of high intensity," so alternate combat-heavy biomes with low-intensity exploration/dialogue/return-to-hub. "After high-intensity boss fights, cutscenes and low-intensity areas feel like rewards." → Sequence biomes so each boss is followed by a calm hub return + story beat. *Sources: [Level Design Book — Pacing](https://book.leveldesignbook.com/process/preproduction/pacing), [Game Developer — level design paper to screen](https://www.gamedeveloper.com/design/level-design-from-paper-to-screen)*

5. **Don't max out the climax mechanically — make the final boss earned, not overwhelming.** Craft guidance cites Dark Souls' final boss as "lots of health but a relatively simple combat style" — challenging yet readable, so victory feels like earned inevitability. For a hobby ARPG, a clear, teachable final encounter beats an unfair spike. *Source: [Level Design Book — Pacing](https://book.leveldesignbook.com/process/preproduction/pacing)*

6. **Teach → Test → Twist each core mechanic.** Introduce a mechanic safely (teach), have the player execute it with prompting (test), then require it in a novel, less-guided context later (twist), spacing repetitions out. Apply to Neverquest's attack/block/roll/swim verbs across the first hour. *Source: [Level Design Book — Pacing](https://book.leveldesignbook.com/process/preproduction/pacing)*

7. **Caveat — prefer "horizontal" context over an isolated 30-min slice for story games.** A pure vertical slice (one polished 30-min chunk) can mislead for narrative games because "players miss the larger context"; a story game benefits from experiencing beats *in sequence*. Implication: scope Chapter 1 as a *thin end-to-end playthrough* (start→climax→resolution), not one over-polished area. *Sources: [Game Developer — iterative narrative design](https://www.gamedeveloper.com/production/iterative-narrative-design-for-video-games-an-indie-approach), [Medium — vertical slice for story-rich games](https://medium.com/@zurichiano/on-developing-vertical-slice-for-a-story-rich-game-ff2ed25f1b79)*

## 2. Quest & Story Gating with Flags / State Machines

**Confidence: High** (state-machine guidance is canonical; quest-pattern academic source adds depth).

1. **Model each quest as an explicit finite state machine: `not-started → active → complete` (plus optional `cancelled`).** "Quests can be converted into state machines to make them more explicit and less error-prone." This directly validates representing quest status as an enum/state rather than scattered booleans. *Sources: [howtomakeanrpg — state machines](https://howtomakeanrpg.com/r/a/state-machines.html), [GameDev.net — implementing stories and quests](https://gamedev.net/forums/topic/652095-help-on-how-to-implement-stories-and-quests-on-an-rpg/5123491/)*

2. **Replace boolean-flag soup with a single enum field — the key rule.** "When you have a handful of flags where only one is `true` at a time, that's a hint that what you really want is an `enum`." Boolean soup produces invalid combinations and conditional logic scattered across methods. Neverquest's `NeverquestStoryFlags` 3-act enum is the right shape; ensure quest status is likewise enum-driven, not parallel booleans. *Source: [Game Programming Patterns — State](https://gameprogrammingpatterns.com/state.html)*

3. **Let each state own its entry/exit actions and its data.** "All of the code for handling a single state is now nicely lumped together." Completion logic, progress tracking, and reward distribution live in the `complete` state, not spread across the codebase. Entry actions (start quest timer/objective) and exit actions (cleanup) are state-local. This aligns with Neverquest's `CLAUDE.md` rule "each system owns its state changes." *Source: [Game Programming Patterns — State](https://gameprogrammingpatterns.com/state.html)*

4. **Gate areas and branch dialogue by querying quest/flag state via getters ("switches").** Shipped 2D RPGs let NPCs and triggers query a global quest state through a getter and branch on it — RPG Maker calls these "Switches"; the same pattern gates which dialogue/area is available based on flag values. This is exactly how a Zelda-like/Stardew-like conditions NPC lines, door access, and event triggers. → Neverquest area entry (warps) and NPC dialogue should *read* `StoryFlags`/quest state, and gameplay events should *write* them (the plan's top-suspected break is flags read-but-never-written). *Sources: [howtomakeanrpg — state machines](https://howtomakeanrpg.com/r/a/state-machines.html), [Situating Quests (academic, design patterns for quests/levels)](https://www.academia.edu/2806300/Situating_quests_design_patterns_for_quest_and_level_design_in_role_playing_games)*

5. **Quests and levels are interdependent — design them together.** Analysis across 20+ RPGs found 33 quest patterns and 57 level patterns that are interdependent: quests carry the story and dictate level setting/contents; levels provide the challenge that completes the quest. "Arrowhead Questing" guides the player from broad to specific objectives. → Don't design Neverquest's biomes and its quest chain separately; each biome should *be* a quest objective with a clear broad→specific goal. *Source: [Situating Quests (academic)](https://www.academia.edu/2806300/Situating_quests_design_patterns_for_quest_and_level_design_in_role_playing_games)*

6. **Persist gate state ("locks stay unlocked").** Once a key/flag opens a gate, the change must persist so players don't re-solve it. → Neverquest's save (flags + scene + player state) must capture quest/flag progression at every transition, or the chapter becomes incoherent on reload. *Source: [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*

## 3. Open-World Connectivity for 2D Top-Down (the recommended model)

**Confidence: Medium-High** (clear consensus on hub-and-spoke for small scope; some sources are forum/discussion-grade — flagged).

1. **Recommended model for a solo/small team + single chapter: HUB-AND-SPOKE.** A central hub (town/crossroads) links to differently-themed "spoke" areas; the player travels outward and returns. The canonical example (Wonder Boy III) has the hero "travel outward from a central town into differently-themed areas." This is the lowest-scope connected-world pattern and *exactly matches* Neverquest's existing `CrossroadsScene` story hub + 5 biome spokes. *Source: [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*

2. **Why hub-and-spoke wins on scope: the hub is a reusable anchor.** "A central hub town reduces scope significantly by serving as your anchor point. Players return here repeatedly, allowing you to reuse assets and navigation patterns while branching into distinct themed regions." For Neverquest this means: re-enable the Crossroads↔biome loop rather than build a sprawling contiguous map. *Source: [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*

3. **Gate spokes with ability/story "lock-and-key"; each unlock opens ≥1 new area.** "Each new ability you grant should unlock access to at least one previously inaccessible area," staggered across the chapter and "ideally occurring at natural narrative or story beats within your hub." → Stagger Neverquest biome access behind `StoryFlag` progression dispensed at the Crossroads hub, not all-at-once. *Source: [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*

4. **Metroidvania (fully interconnected, ability-gated backtracking) is higher craft cost — defer it.** Metroidvania worlds "feel more handcrafted" and "respect the player's time," but require careful interconnection, backtracking design, and a mazelike map revealed gradually — more design overhead than a single chapter warrants. Hub-and-spoke gives most of the "connected world" feel at a fraction of the wiring cost. *Sources: [ResetEra — Onimusha level design discussion](https://www.resetera.com/threads/level-design-in-a-new-onimusha-open-world-metroidvania-hub-based-or-linear.72122/), [TIGSource — metroidvania in 2D top-down](https://forums.tigsource.com/index.php?topic=66609.0)* *(forum-grade — flagged as discussion, not authority)*

5. **Add light non-linearity via overlapping paths, not more content.** "Design overlapping paths between hub and spokes" and "allow players multiple routes" to create exploration rewards "without requiring additional content." → Once ≥2 biomes are open from the hub, let the player choose order; that single affordance reads as "open world" cheaply. *Source: [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*

6. **When to choose hub-and-spoke vs. linear-with-branches:** choose **hub-and-spoke** when you have several discrete themed areas and want re-visitation/persistence (Neverquest's case — 5 biomes already scaffolded); choose **linear-with-branches** only if Chapter 1 collapses to a single corridor. Given Neverquest's existing Crossroads + biomes, hub-and-spoke is the strictly better fit. *Source: [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*

## 4. Phaser 3 Scene Management for World Transitions

**Confidence: High** (official Phaser docs + samme's authoritative FAQ; directly applicable).

1. **`scene.start(key, data)` REPLACES the current scene; `scene.launch(key, data)` runs a scene IN PARALLEL.** "scene.start() stops the current scene and starts a new one (a replacement operation)"; "scene.launch() launches the given Scene and runs it in parallel … at the next Scene Manager update, not immediately." → Use **`scene.start`** for biome/world transitions (leaving the hub for a biome); use **`scene.launch`** for HUD/QuestLog/Journal/dialog overlays that sit *on top of* gameplay. The plan flagged `QuestLogScene`/`JournalScene` as never `launch`ed — this is the correct verb to wire them in without destroying the gameplay scene. *Sources: [Phaser ScenePlugin API](https://docs.phaser.io/api-documentation/class/scenes-sceneplugin), [samme — Phaser 3 Scenes Summary gist](https://gist.github.com/samme/01a33324a427f626254c1a4da7f9b6a3), [phaser3-faq wiki — Scenes](https://github.com/samme/phaser3-faq/wiki/Scenes)*

2. **Use the global Registry (Data Manager) for cross-scene persistent state — fully decoupled.** "The Game has a Registry instance you reference from a Scene via `this.registry` … for easy cross-Scene data exchange." Set with `this.registry.set('key', value)`; subscribe with `this.registry.events.on('changedata', cb, this)` (callback gets `(parent, key, data)`). → Story flags, current-chapter state, and player progression that must survive `scene.start` transitions belong in the registry (or a manager scene), NOT instantiated per-gameplay-scene. This corroborates the plan's concern that `NeverquestStoryFlags` is currently instantiated only inside UI scenes. *Sources: [Phaser docs — Cross-Scene Communication](https://docs.phaser.io/phaser/concepts/scenes/cross-scene-communication), [Ourcade — communicate between scenes](https://blog.ourcade.co/posts/2020/phaser3-how-to-communicate-between-scenes/)*

3. **Pass per-transition data via the second arg to start/launch, consumed in `init(data)`.** A scene receives transition data in `init(data)`/`create(data)`. → Warps/doors should pass target spawn point, source scene, and entry context as scene data (e.g., `this.scene.start('IceCavernsScene', { fromWarp: 'crossroads_north', spawn: 'south_gate' })`) so the destination spawns the player correctly. *Sources: [html5gamedevs — passing data to init on start](https://www.html5gamedevs.com/topic/36148-phaser-3-scene-phaser-2-state-passing-data-to-init-when-start/), [samme gist](https://gist.github.com/samme/01a33324a427f626254c1a4da7f9b6a3)*

4. **Keep a persistent "manager"/boot scene always active for shared state + music.** The docs demonstrate a UIScene running alongside the GameScene with `active: true`; "persistent scenes like audio managers continue playing background music during scene transitions," and an always-active controller scene can respond without a frame delay (the Scene Manager iterates top scenes first). → A single persistent Neverquest manager scene (or HUDScene) should own music + the live `StoryFlags`/save reference so they survive every world `scene.start`. *Sources: [Phaser docs — Cross-Scene Communication](https://docs.phaser.io/phaser/concepts/scenes/cross-scene-communication), [Phaser docs — Scenes](https://docs.phaser.io/phaser/concepts/scenes)*

5. **Door/warp systems: read targets from Tiled object properties, then `scene.start` with data.** Phaser API doesn't ship a "warp" primitive; the established pattern is to place warp/door objects in the Tiled map with custom properties (target scene key, target spawn), detect overlap, and call `scene.start(targetKey, { spawn })`. The research-plan explicitly warns that static `grep` for `scene.start('X')` misses these runtime-resolved targets — so Neverquest's `NeverquestWarp` reading `goto`/scene-change props is the *correct* and expected pattern, just under-connected. *Sources: [Phaser ScenePlugin API](https://docs.phaser.io/api-documentation/class/scenes-sceneplugin), [generalistprogrammer — Phaser scene tutorial](https://generalistprogrammer.com/tutorials/phaser-scene-management-tutorial)*

6. **Use `scene.transition()` for polished area changes; prefer events over hard scene references.** `scene.transition()` runs a timed transition between two different scenes (target can sleep or stop afterward — default stop). For decoupling, prefer the Registry/EventEmitter over `this.scene.get('OtherScene').events` (which couples the two scenes). → For chapter coherence, a manager scene + registry events scale better than scene-to-scene references as biome count grows. *Sources: [samme gist](https://gist.github.com/samme/01a33324a427f626254c1a4da7f9b6a3), [Ourcade — communicate between scenes](https://blog.ourcade.co/posts/2020/phaser3-how-to-communicate-between-scenes/)*

## 5. Pitfalls — "feels like a game" vs. tech demo; scope control

**Confidence: High** (strong, consistent indie-postmortem consensus).

1. **The #1 killer is scope, not polish — 70%+ of surveyed indies cite "scope too large" for missed deadlines/abandonment.** Set hard constraints, keep a tight feature list, and cut anything that doesn't strengthen the core mechanic. → For Neverquest, hold Chapter 1 to the minimum-coherence bar (per research-plan §7); exclude crafting/economy/skill-trees. *Sources: [Wayline — scope creep in indie games](https://www.wayline.io/blog/scope-creep-indie-games-avoiding-development-hell), [Wayline — scope rules for solo devs](https://www.wayline.io/blog/essential-scope-rules-solo-game-dev)*

2. **A pile of systems is a tech demo; a *core loop* is a game.** The cautionary postmortem: a dev spent six months on a brilliant combat system that "never launched … the game itself lacked a core loop — without a story, quests, or even basic exploration, it was merely an isolated feature." → Neverquest's exact risk per the plan: many implemented-but-orphaned systems (Crossroads, biomes, QuestLog, story flags). Wiring them into one reachable loop (hub → quest → biome → boss → flag advance → return → next) is what converts demo→game. *Source: [Wayline — scope creep buried my first game](https://www.wayline.io/blog/scope-creep-buried-my-first-game)*

3. **Finish Chapter 1 end-to-end before improving anything later.** "Finishing Chapter 1 is more valuable than improving Chapter 7 that does not yet exist." Focus on "the smallest version of your game that is complete, playable, and coherent." → Prioritize a reachable start→climax→resolution over deepening any single biome. *Source: [Wayline — scope creep in indie games](https://www.wayline.io/blog/scope-creep-indie-games-avoiding-development-hell)*

4. **Define the single most enjoyable action and perfect it before secondary features.** "Define the single most enjoyable thing a player will do … focus on perfecting that before even considering adding secondary features." For an ARPG that is moment-to-moment combat + exploration; everything in Chapter 1 should serve that loop. *Source: [Manuel Sanchez — scope creep in game dev](https://manuelsanchezdev.com/blog/scope-creep-game-development/)*

5. **Coherence pitfall specific to flag systems: flags read but never written.** Implied directly by Section 2's gating pattern — if NPCs/areas *query* quest state but no gameplay event *sets* it, quests can never complete and the chapter dead-ends. This is the research-plan's top-suspected break; the literature confirms the symptom is a classic incoherence bug. *Source: [howtomakeanrpg — state machines](https://howtomakeanrpg.com/r/a/state-machines.html) (read-vs-write quest state)*

6. **Write a small design doc / gating spreadsheet and stick to it.** "Define the core features upfront and create a comprehensive design document and stick to it"; for lock-and-key worlds, "document your gating spreadsheet carefully to avoid blocking players unintentionally." → A one-page Chapter 1 beat→flag→quest→scene→warp table (the Q3 deliverable) is itself the recommended anti-scope-creep artifact. *Sources: [Manuel Sanchez — scope creep](https://manuelsanchezdev.com/blog/scope-creep-game-development/), [Game Developer — World Design for 2D Action-Adventures](https://www.gamedeveloper.com/design/book-excerpt-world-design-for-2d-action-adventures)*
